# Opero 需求（v0.4，2026-11-22）

> Opero is an open-source, chat-first admin platform powered by AI employees.
> Opero 是一个以聊天为入口、由 AI 员工驱动的开源后台管理系统。口号：和 AI 团队聊天，管理你的业务。
>
> 本文是用户和代码助手多轮讨论后定下来的需求和设计方向，还没开发。开发按这里来，改需求先改这份文档。
> 来源：现有的 KidLock 超级后台（下面叫「旧后台」）。**Opero 是重新设计**，不是在旧后台上改，也不沿用旧表结构（第 11 节）。
> 配套：界面草图 4 张（`opero-1-网页.jpg`、`opero-2-桌面客户端.jpg`、`opero-3-手机.jpg`、`opero-4-员工-申请-开机向导.jpg`），建议放进 `docs/界面草图/`。

## 0. 定位和原则

**Opero 核心只解决三件事**（2026-11-21 定，排优先级、取舍功能都按这三条）：
1. **定规范**：员工、工具、插件、表单、卡片、Agent 之间怎么说话，定成清楚的规范（以 MCP 为底），别人照着就能接。
2. **漂亮界面**：网页 / 桌面 / 手机一套好看、好用的聊天界面和表单组件。
3. **支持二开**：底层扩展点做实，使用者按规范加插件、加员工、加规则，不用改内核。

**个人开发助理，一人一套**（2026-11-22 已定）：试用和思考后，多账号不对——权限无论如何都很难做完美，还会让整件事变复杂、难用。Opero 定位成**个人开发助理**：每个人部署自己的一套，**只有主人一个账号**，没有用户 / 角色 / 授权 / 申请 / 审批。团队用 = 每人一套，共享的东西放 git（项目仓库、员工模板和规矩）。
  - **主打个人版**（已确认）。好处一：**每个人习惯不同，可以在我们的底座上自由二开**（自己 fork、让「后台开发」员工改自己的那套，官方升级再合并上来）——底座把规范、扩展点、文档做扎实，个性化交给每个人。
  - 好处二：**权限 = 你本人在公司的权限，带进来**。Opero 自己不发明权限：你有哪台服务器、哪个库、哪个仓库的账号，就把凭证加进来，员工就能用；你没有的，Opero 里也没有。公司那边收回你的权限，Opero 里自然也用不了。下面凡是讲「管理员 / 普通用户 / 授权 / 申请 / 自动审核」的内容都按这条作废（第 5 节已重写）。

**主要用户是研发团队**（2026-11-21 说明）：出发点是解决开发的问题——开发、运维、发布、排查、查库修数据。运营等业务人员不是第一版目标，以后靠二开 / 插件。

**北极星：在手机上查 bug → 改代码 → 发布，全部搞定**（2026-11-21 已定）。第一版的规范、界面、功能都拿这条线检验，详见 `主线场景.md`。

**后台只是一个业务功能**（2026-11-21 已定）：「管好了开发，所谓后台，只是一个业务功能，要怎么做都行。」Opero 内核不做传统后台那些业务功能（业务数据增删改查、报表、审批流……），这些由开发员工给各产品做出来（产品代码里或 Opero 插件）。内核只把开发管好。

**信任 AI、少审核**（2026-11-21 定）：有权限就直接做，员工之间互相调用自动进行；只有「发起人没权限」和「危险操作」才找人；人只看结果，工具和 AI 之间的过程不给人看（全进审计）。

- 传统后台是「菜单 → 页面 → 按钮」；Opero 是「员工 → 聊天 → 员工去做」。进去就是微信那样的聊天界面；每个功能都有一个 AI 员工管理，每个员工对应一个常驻 work。
- **面向小团队，不求做全**：内置的功能简单好懂、开箱即用；**底层做实、扩展性做好**，满足不了的让使用者自己二开（第 9 节扩展点）。
- 我们提供的是「新的后台操作方式」，不是一个什么都有的大后台。

## 1. 核心概念（产品里统一用这几个词）

| 概念 | 是什么 |
|---|---|
| **员工** | 负责具体业务的 AI：职责（提示词）、执行器（Claude Code / Codex / …）、人设、能用的工具、底部菜单和面板 |
| **工作空间** | 员工常驻的 work：一个 git 仓库 + 它在哪台服务器的哪个目录。员工自己的仓库（记忆、规矩、交接）是它的工作空间；业务代码仓库（各产品项目）也是工作空间 |
| **会话** | 下达任务、查看结果、审批都在这里；消息、文件、卡片、表单都是会话里的一条 |
| ~~授权~~ | （作废：单用户，不做授权 / 申请；安全见第 5 节） |
| 资源 | 服务器、工作空间、应用和环境、域名、云账号、数据库……（插件可以加新类型） |
| 凭证 | 账号密码、密钥、Token、证书（凭据中心） |

**员工、资源、凭证三样互相独立**：员工删了资源和凭证不受影响，反过来也一样。

## 2. 核心闭环（第一版必须走通）

1. **一键部署 web**（一条命令或 Docker，第 10 节），装完同时把这台服务器的 Agent 装好、接好。
2. **通过 Agent 打通 CLI**：聊天里的卡片引导选执行器（Claude Code / Codex）和认证（订阅 / API Key），Agent 自动建开发用户和工作区、装 CLI、跑一句测试，通了才算完成。新部署都要做这一步（授权 Claude Code）。
3. **把后台自己的代码拉到服务器**：填 Opero 仓库（使用者先 fork 一份）地址，拉成工作空间 `opero`。
4. **快速建第一个员工：系统管家**：建员工、改设置、管凭据和插件都可以跟它说。它的记忆先放服务器本地 git，以后再接远端。
5. **建「后台开发」员工**：知道所有规矩（规矩写在 opero 仓库里），缺功能自己开发（第 9 节的安全要求）。

目标：从一台空服务器到能和系统管家聊天，10 分钟以内。

## 3. 界面：像微信服务号（网页 / 桌面客户端 / 手机三端一致）

- 一级导航只有：**会话 · 员工 · 工作空间 · 应用（插件面板）· 我**。没有传统菜单树。网页、桌面在左边竖排，手机在底部页签。
- 会话列表像微信：员工头像 + 名字 + 最后一句 + 时间；状态点（绿 = 在干活、橙 = 等你）；红点未读（免打扰的不算）；置顶；「接口会话」等收成一组（像订阅号）。
- 每个员工的聊天里三层：

| 层 | 用法 | 经不经过 AI |
|---|---|---|
| 聊天 | 说话让员工做事、问它 | 经过 |
| 卡片 / 表单 | 员工回复里带的确认、申请、选择、填写 | AI 拿出来，点了由系统直接执行 |
| 底部菜单 | 像服务号底部那排按钮：列表、记录、状态… 点了直接开面板 | 不经过，秒开 |

- 看列表、看详情、点固定操作走面板；要理解、要判断、要多步骤的才找 AI（常驻 work 第一句回复要 10～30 秒，不能什么都等 AI）。
- 聊天顶栏：员工名、职责一句话、执行器、跑在哪台、工作空间；「在做什么」显示在会话中间一行小字（在执行命令 / 在核对…），随时能插话、停止。
- 面板：网页从右边滑出、不离开聊天；手机全屏推入，返回回到聊天。
- **网页**：三栏（导航 · 会话列表 · 聊天，面板从右滑出）。
- **桌面客户端**：同一套网页套壳（像微信桌面版），多了系统通知（只推出错、要你决定的）、托盘「等我处理」、Dock / 任务栏未读、全局快捷键、拖文件、截图直接发、开机自启（可关）。
- **手机**（安卓先做）：四个底部页签（会话 · 员工 · 工作空间 · 我）；按住说话（松开就发、上滑取消）；表单从底部弹出；验证本人用指纹。
- 第一次打开：**开机向导就在聊天里**，一步一张卡片（主人账号 → 接入服务器 → 接 Claude Code → 拉 Opero 代码 → 系统管家 → 后台开发员工）。
- 主题浅色 / 深色；每个员工可设头像、名字、聊天背景。界面英文优先、中文同步。

## 4. 员工

- 每个功能一个员工，一个员工一个常驻 work（工作空间 + 常驻会话）。参考分法：系统管家（用户、员工、设置、凭据、审核）· 运维（服务器、环境、资产）· 发布（应用、环境、流水线、签名证书）· 日志值班（按产品）· 内勤（邮件、IM）· 项目助理（新项目、资产、想法）· 产品运营（按产品，管业务数据）· 总调度（理解需求、拆任务派给员工、跟进，自己不执行）。
- （作废：单用户，不需要「谁能用」和多人共用员工。）
- 员工派活给员工（总调度派给发布）：身份沿用最初发起的那个人。

### 4.1 员工的底座能力（2026-11-22 提出，界面已做）
- **消息助理**：专门一个员工管所有外部消息（邮件、Slack、Telegram、飞书、企业微信、钉钉），只查、只整理：一键到原处主人自己回；要时给回复建议（多语言，复制用）；**默认不起草、不代发**，代发是每个渠道的开关、默认关；Opero 的通知也能发到这些渠道。
- **换 work**：work 太长（上下文满 / 卡住 / 换服务器）就换：旧的写交接提交到 git，新的读交接接着干。
- **记忆仓库**：每个员工一个 git 仓库（`emp-名字`），换 work、换服务器、重装都不丢。
- **聊天设置**：每个员工单独设头像、名字、背景、提醒（默认只提醒要你决定的）、置顶；少红点。
- **还有**：自己的电脑用同一个 Agent 接入、知识库（通用规范、接口文档等放数据库，员工通过 MCP 按需查；必读的短规矩每次派活自动带上；员工自己的记忆仍在它的 git 里，见 `MCP设计.md` 第 9 节）、成本预算、员工模板分享、流程沉淀（做过的事下次不经过 AI）、AI 不可用时备用执行器。**不做**：备份搬家、待办日程（2026-11-22 已定）。
- 详见 `底座缺口.md`。

## 5. 安全（单用户版，2026-11-22 重写）

只有主人一个人，**没有账号、角色、授权、申请、审批**。要防的只剩一件事：AI 被日志、邮件、网页内容诱导去做危险的事。用下面四样就够，而且都不打扰日常：

| 机制 | 怎么做 |
|---|---|
| **风险三级**（每个工具在代码里声明） | 读、写：直接做；**危险**（看密钥明文、删资源、大批量改数据、改 Opero 的安全代码）：永远要主人本人验证，不能自动 |
| **每个员工的审核方式**（work 设置，选了就记住） | 自动（默认，信任 AI）/ 改文件自动、跑命令要问 / 每一步都问 / 只看不改 |
| **生产保护**（默认关，可开） | 打开后，员工改生产（发版、重启、改配置、改数据）先出确认卡片 |
| **操作记录 + 撤销**（原「审计」） | 员工做的每件事都记一条，只能追加；改数据有快照、合并能撤销、发布能回滚 |

- 验证本人：网页 / 桌面通行密钥（指纹），手机指纹，30 分钟内有效；只有 IP 没 HTTPS 时用密码 + 两步验证码。
- AI 永远拿不到凭证明文，只拿编号，由工具在后台或 Agent 里用；看明文只能主人在界面上点、强验证。
- 防线写在代码里，不靠提示词：AI 就算被诱导，危险操作也一定停下来等人。
- 环境只做标签（开发 / 测试 / 生产），用于生产保护和提醒。
- **权限边界 = 主人带进来的凭证**：员工能碰的资源，就是主人在公司本来就有、并加到凭证里的那些（服务器 Agent 令牌、数据库账号、代码仓库令牌、云账号）。Opero 不另设一层权限，也就不会比主人本人权限更大。
- 唯一判定函数（第 9 节）保留，作为二开扩展点；默认规则只有上面这些。

## 6. 会话、卡片、表单

- 所有东西都是会话里的一条：文字、文件、「在做什么」、卡片、表单。
- **表单用 MCP Apps**：后台的表单按功能基本固定（新建应用、发布、申请资源、改设置…），每个插件把自己的表单做成界面资源（如 `ui://release/publish`），工具声明用哪个界面；AI 调工具时聊天里嵌着显示、带 AI 预填的数据（标「AI 填的」）；底部菜单打开的是同一个界面（不经过 AI）。
  - 表单跑在沙箱里（网页 iframe、App WebView），不能自己联网、不能直接调后台；要做的事都经宿主转成工具调用，宿主统一做判定（第 9 节）、验证本人、审计。
  - 操作类表单提交后系统直接执行，变成只读摘要卡留在会话里；回答类表单（AI 干到一半问你）把结果交回 AI。
  - 密码、密钥类字段直接存进凭据中心，AI 只拿到引用。
  - 宿主把主题、语言、当前用户标签传给表单。
  - 做一套 Opero 表单组件库（输入、下拉、选服务器 / 应用 / 凭证 / 员工、表格、确认区）。
  - App 用 WebView 显示表单，App 原生只实现一次宿主层，以后加表单不用发 App。
- **临时提问兜底**：AI 临时要问的（选方案、补一句）做一个通用「提问」工具：几个简单字段自动画成表单；AI 调它 → 聊天里出表单 → 工具等着 → 提交后作为工具结果返回（执行器在服务器上无界面运行，不能依赖客户端画）。

## 7. Agent 与执行

- **Agent 必装**（Go）：服务器主动连出来不开端口、后台不握 root 钥匙；禁编译 / 资源上限 / 只读识别 / 敏感文件拒读在本机拦；实时心跳和监控；内网机器、个人电脑也能接。
- Agent 负责：连接后台、执行与只读查询、在沙箱里跑执行器（Claude Code / Codex）、资源上限、监控上报、自动升级。
- 派活：会话说一句 → 后台排队 / 插话 → 下发给那台的 Agent → 执行器经 Opero 的 MCP 工具调后台能力（每次过判定、记审计）→ 结果、文件、卡片流回会话。
- 「禁编译、禁自测、资源上限」按每台服务器的策略执行，可手动放开（开发员工的预览需要）。
- 员工记忆在它自己的 git 里；git 支持 Codeup、GitHub、Gitea。
- 开源用户不能用 claude.ai 订阅登录给别人提供服务，文档默认引导填 API Key；自用部署可以用订阅。

## 8. 插件 & 后台开发员工

- **插件**一份清单：自己的表（带编号的 SQL，表名带插件前缀）、工具（属于哪个员工、动作名、风险级别、用哪类资源）、表单和面板（MCP Apps）、底部菜单、定时任务、员工模板、新的资源类型、设置项、中英文文字。
- 开源自带插件：服务器与 Agent、凭证、发布、云（AWS / 阿里云）、通知渠道。私有插件（不进开源仓库）：产品日志值班与问题清单、邮件、IM、个人待办等。
- **后台开发员工改的是它自己运行的系统**，必须：
  1. 规矩写在 opero 仓库里（开发必读、技术文档、CLAUDE.md），每次开工先读；
  2. 新功能优先做成插件，不改内核（插件坏了停掉就行，内核照常跑，也不和官方升级冲突）；真要改内核走单独审批或给官方提合并请求；
  3. 先预览再上线：分支改完起一个预览实例（不同端口、测试库），聊天里发卡片「改了什么 + 预览链接 + 改动对比」，主人点「上线」才发正式的；
  4. 上线坏了能自己救：保留上一版，启动后健康检查，不通过自动回滚；网页打不开也能用 `opero rollback` 回到上一版；
  5. 不能改操作记录、验证本人这些安全代码，要主人单独确认。
- 使用者 fork 后，官方新版由开发员工负责合并上来、先预览再上线。

## 9. 底层要做实的扩展点（二开靠它们）

1. **所有动作只过一个判定函数**：`判定(通过哪个员工, 动作, 资源) → 允许 / 要确认 / 拒绝（带原因）`。AI 调工具、表单提交、底部菜单按钮全走它。默认规则只有第 5 节那几条；二开在这里挂自己的规则，不用改别处。
2. **工具自己声明**：属于哪个员工、动作名、风险级别、用到哪类资源；插件加的工具照样被判定、被审计。
3. **资源类型可扩展**：服务器、凭证、工作空间内置；插件可注册新类型（店铺、设备、订单…），自动接上判定和操作记录。
4. （作废：单用户，没有角色。）
5. **审计完整**：一条不落。

## 10. 部署

- **一键命令**：`curl -fsSL https://get.opero.dev | bash`（地址待定）
  检查系统（Linux x86_64 / arm64，建议 2 核 4G+）→ 没有 Docker 先问再装（国内自动换源）→ 问域名（可空）和你的邮箱 → 生成数据库密码、**加密钥匙**、首次登录一次性口令 → Docker 起后台 + 网页 + MySQL + HTTPS → **在宿主机装好 Agent 并自动注册**（`--no-agent` 跳过）→ 打印访问地址、一次性口令、备份钥匙提醒。
- **Docker**：`docker compose up -d`；镜像 `opero`（后台 + 网页一个镜像）、`mysql:8`、`caddy`（有域名自动 HTTPS）；数据卷 `db`、`files`、`keys`。这种方式开机向导里给 Agent 接入命令。
- **管理命令 `opero`**：`status` · `upgrade`（拉新版 → 改表 → 健康检查，不过自动回滚）· `rollback` · `backup` / `restore`（数据库 + 文件 + 加密钥匙一起）· `logs` · `reset-owner`（指纹丢了在服务器上重置）· `import --from kidlock`。
- 注意：指纹登录只在 HTTPS 下能用；加密钥匙丢了凭证全废，安装后和每次升级前提醒备份；镜像同时发 Docker Hub 和阿里云镜像仓库；开源版用 GitHub Actions 构建镜像和 Agent。

## 11. 和旧后台的关系：重新设计，不迁就旧表

- **不用迁就旧后台的数据结构**：表结构、权限模型、消息和卡片格式都按 Opero 自己的概念设计。
- 主人自己搬过来：**导入工具** `opero import --from kidlock`，导入一次就用新系统：
  - 读旧库，把账号、服务器、凭证、员工（提示词、人设、授权的机器 / 库）、工作空间（项目、仓库地址）、Claude 订阅 token 等转成新结构；
  - 凭证用旧后台的加密钥匙解开、再用 Opero 的钥匙重新加密；
  - 会话聊天记录可选导入（只读归档）；
  - 导完列一份清单：哪些搬过来了、哪些要手动补。
- Agent 协议可以重新设计；迁移时每台服务器重跑一条新的接入命令（能做到的话让旧 Agent 自动升级成新的，待定）。
- 切换：导入 → 核对清单 → 停旧后台 → 切域名。

## 13. 分几步做（每步都能单独用）

1. 内核：一键部署、开机向导、Agent 接入、CLI 打通、工作空间、员工 + 会话、安全（风险级别 / 判定 / 审核方式 / 生产保护 / 验证本人）、聊天界面 + 卡片 + 表单 + 底部菜单、审计 → 能拿它当日常入口。

3. 服务器 / 凭证 / 发布 / 云插件（从旧后台搬，可以让开发员工搬）。

5. 导入工具（从旧后台搬数据）。

## 14. 还没定的

1. 开源许可：AGPL（防别人拿去做收费云服务）还是 MIT / Apache-2.0。
2. 新旧并存：建议 Opero 的聊天、员工、权限能日常用以后，旧后台只修 bug，新功能只做在 Opero。
3. 一级导航要不要单独加「等我处理」；底部菜单最多几个（建议 3～4，多的收进「更多」）。
4. 桌面壳用 Tauri（小、快）还是 Electron（生态全）。
5. 配色（草图先用了紫色系）。
6. 预览实例放同一台服务器还是单独测试机。
7. 默认分支：仓库现在是 `master`，旧后台是 `main`，要不要统一。
8. 数据库：仓库说明写的是阿里云 RDS 生产实例上的 `opero` 库；开发阶段建议先用测试库，至少给 opero 单独账号、只能碰 `opero` 库。
9. 迁移时旧 Agent 能不能自动升级成新 Agent。
