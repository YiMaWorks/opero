# 传统后台 → Opero：对照和缺口（2026-11-21，研究稿）

> 目的：把传统后台（若依 / Ant Design Pro / 各公司自研后台这一类）常见的功能逐项对到 Opero 的「员工 + 会话 + 工作空间 + 插件」上，找出**还缺什么**。
> **2026-11-21 更正**：说明 Opero 出发点是**解决开发的问题**（研发团队：开发、运维、发布、排查），不是给运营用。所以下面 A.1「业务数据接入和数据面板」改为「开发查库和修数据」（见 `规范/数据.md` v0.2），运营用的实体 / 业务数据面板降为二开；组织架构、审批流、单点登录这类面向业务人员的更往后放。其余缺口（撤销、触发器、首页概览、AI 成本 / 并发等）不变。
>
> 结论先行（原稿）：「管人、管权限、管资源、看日志」这类**管理面**，Opero 基本都覆盖了，只是换了方式；真正缺的是两块——**① 业务数据怎么接进来、怎么批量看和改**（传统后台的主业），**② 信任 AI 以后的安全网和 AI 自己的管理**（成本、并发、撤销、主动触发）。

## 〇、最终结论（2026-11-21，以这一节为准，下面是分析过程）

原话：**「管好了开发，所谓后台，只是一个业务功能，要怎么做都行。」**

- Opero **不和传统后台比功能**。传统后台的那些东西（业务数据增删改查、报表、审批流、组织架构、导入导出、字典……）都是「业务功能」，是 Opero 里的**开发员工给各个产品做出来的东西**：做在产品自己的代码里，或者做成 Opero 插件，要什么样都行。
- 所以 Opero 内核只管一件事：**把开发管好**——让 AI 员工能可靠地开发、发布、运维、排查、查库修数据，人只看结果。
- 下面对照表里标 ❌ / ⚠️ 的业务类缺口**都不进内核**；还保留的是「管好开发」本身需要的：
  1. 撤销 / 改动历史（少审核的安全网，含修数据的快照撤销）；
  2. 触发器（报警、Webhook、定时 → 员工自己动）；
  3. 首页概览（「等我处理」+ 各员工状态）；
  4. AI 自己的管理：成本用量、员工并发、执行质量、流程沉淀、共享知识库、AI 不可用时降级；
  5. 开发管理本身可能还缺的（待讨论）：需求 / 任务跟踪（一句话 → 任务 → 分支 → 提交 → 发布串起来）、代码审查和合并、任意项目的预览环境、项目文档规范（每个工作空间的交接 / 设计文档约定）。

## 二、缺口（按重要程度）

### A. 必须补（不补就不能代替传统后台）

1. **业务数据接入和「数据面板」规范** — 传统后台 80% 的时间是在看列表、筛选、改一条、批量改。Opero 现在只说「产品运营员工管业务数据」，没说数据从哪来、面板长什么样。要补：
   - **数据源**当资源：业务库（MySQL / PG）、业务系统的 HTTP 接口；只读 / 可写分开授权。
   - **实体声明**：表 / 接口 → 字段、类型、哪些能筛选、哪些能改、显示名（AI 能根据表结构自动生成初稿，人确认）。
   - **通用数据面板**：列表（筛选、排序、分页、列选择）、详情、编辑、批量操作、导出——按实体声明自动出，不用每个都写代码。这是「漂亮界面」里最重要的一块组件。
   - 跟 AI 的分工：**看、筛、点固定按钮走面板（秒开、不花钱）；要理解、要判断、跨表分析找员工**。员工也能用同一份实体声明查和改数据（走工具、过判定、记审计）。

2. **撤销和改动历史（信任 AI 的安全网）** — 我们少审核，就必须「做错了能退回来」。要补：
   - 写操作工具声明「怎么撤销」（`undo`：反向操作，或执行前存快照）；
   - 会话里每个写操作结果带「撤销」按钮（一定时间内）；
   - 业务数据改动留前后值（审计里已有参数摘要，要加改前 / 改后）。
   - 这一条和「信任 AI、少审核」是一对：**审核少了，撤销要强**。

3. **主动触发（事件 → 员工）** — 传统后台是人去点；AI 后台应该是事情来了员工自己动。现在员工只会被人在会话里叫醒。要补统一的「触发器」：
   - 定时：员工的定时活（每天 9 点巡检、每周一出周报）；
   - Webhook：外部系统推事件（GitHub、监控报警、支付回调）→ 交给指定员工；
   - 监控阈值：Agent 发现内存 / 磁盘 / 报错超阈值 → 交给运维 / 值班员工；
   - 邮件 / IM 进来的消息 → 内勤员工。
   - 触发出来的活：员工做完只在**需要人知道**时才发到会话（符合「人只看结果」）。

4. **首页 / 概览** — 管理者打开要一眼看到「现在怎么样」。不做传统仪表盘，做成：
   - 「等我处理」（需求第 14 节第 3 条已提）+ 各员工一句话状态 + 今天的关键数字；
   - 数字和图表由员工定期生成（日报卡片），或插件声明「概览卡片」；
   - 也就是报表 = 员工产出的卡片 / 文件，不单做报表模块。

### B. AI 后台特有、传统后台没有、我们也还没设计

5. **AI 成本和用量** — 每个员工、每个人、每个任务花了多少 token / 钱；预算上限（到了停或降级）。用 API Key 计费后这是刚需。
6. **员工并发** — 多人同时找同一个员工：共用一个工作空间（一份 git），同时跑会互相改坏。要定：每个会话一个 git worktree / 排队 / 只读任务并行。
7. **员工的执行质量** — 任务成功率、耗时、失败原因，用来调提示词、换执行器。审计里有原始数据，要一个汇总。
8. **把做过的事沉淀成固定流程** — AI 第一次做「每月对账」要思考，第二次应该照流程跑，最好能不经过 AI（快、便宜、确定）。要一个「流程 / 技能」概念：员工把做过的事存成脚本或步骤，下次直接调；对应各执行器的 skills 机制。
9. **共享知识库** — 员工记忆各在自己的 git 里；公司级的资料（产品说明、规矩、客户信息）所有员工都要用。要定放哪、怎么检索。
10. **AI 不可用时的降级** — API 欠费、限流、执行器挂了：面板和底部菜单照样能用（不经过 AI），会话里提示「员工暂时不在」，自动换备用执行器（可选）。

### C. 可以交给插件 / 二开（内核只留扩展点）

组织架构和数据权限、业务审批流、单点登录（企业微信 / 钉钉 / 飞书）、字典、多租户、手机推送渠道（国内厂商推送）、文件存储后端（OSS / S3）。内核要保证的是：**判定函数能挂规则、登录方式能扩展、存储后端能换、通知渠道能加**。

## 三、对三件核心事的影响

| 缺口 | 定规范 | 漂亮界面 | 支持二开 |
|---|---|---|---|
| 数据源 + 实体声明 + 数据面板 | 新增「数据规范」 | 新增通用数据面板组件（列表 / 详情 / 编辑 / 批量 / 导出） | 二开最常做的事：接自己的业务库 |
| 撤销 / 改动历史 | 工具规范加 `undo` | 结果卡片带「撤销」 | 插件工具照规范声明就自动有 |
| 触发器 | 新增「触发器规范」（定时 / Webhook / 监控 / 消息） | 员工档案里能看、能开关 | 插件可注册新的触发源 |
| 首页概览 | 插件可声明「概览卡片」 | 首页 / 「等我处理」 | 插件加卡片 |
| 成本、并发、质量、流程沉淀、知识库、降级 | 员工规范里补 | 员工档案页 | — |

## 四、建议

- `方案路线.md` 的规范清单加两份：**数据规范**（数据源、实体声明、数据面板）、**触发器规范**；工具规范里加 `undo`；员工规范里加成本、并发、流程沉淀、知识库。
- 「数据面板」做成 Opero 界面上最用心的组件之一——它是传统后台用户搬过来时最直接的感受。
