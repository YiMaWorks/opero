# Opero MCP 底层设计（草案 v0.3，2026-11-21）

> 状态：**研究方案阶段，没开发**。这是 Opero 里「AI 和系统、AI 和 AI、AI 和人」交流的底层约定，其它模块（员工、权限、插件、表单）都建在它上面。
> 依据：`需求.md` 第 5、6、7、8、9 节。规范事实见 `调研-MCP现状.md`（2026-11-21 查，带出处）；执行器能力见 `调研-agent-CLI.md`。
> 改这份文档 = 改系统的地基，改之前先在 `交接.md` 写原因。
> v0.3 改动（已定的）：**信任 AI、少审核**——有权限就直接做，员工之间互相调用自动进行；工具和 AI 之间的过程不给人看；只按 MCP 最新版做，不做旧版兼容。

> **v0.4 更正（2026-11-22）**：Opero 改成**个人开发助理，一人一套，只有主人一个账号**。下文所有「发起人有没有权限 / 管理员 / 普通用户 / 授权 / 申请 / 自动审核 / pending_approval」一律作废。判定的默认规则变成：读、写 → 直接做（按员工 work 的审核方式：自动 / 改文件自动命令要问 / 每步都问 / 只看不改）；危险 → 主人本人验证；生产保护打开时改生产先确认。统一结果里的 `pending` 只剩「等你确认」一种。`ctx.origin_user` 永远是主人，保留字段只为记操作记录。

## 0. 一句话 + 原则

**Opero 后台就是一个 MCP 服务器**：员工（Claude Code / Codex 等执行器）、表单（MCP Apps 界面）、外部客户端，全部通过 MCP 调同一套工具；每次调用都经过**同一个网关**：认出是谁 → 判定 → 审计 → 执行。AI 之间不直接说话，都通过 Opero 的工具中转，所以每一次都有身份、有判定、有审计——但**这些都在后台默默做，不打扰人**。

三条原则（优先级从高到低）：
1. **信任 AI，有权限就直接做**。发起人有权限、员工有授权 → 直接执行，不出卡片、不问人。员工之间互相派活、互相调工具也一样，自动进行。
2. **只有两种情况才停下来找人**：① 发起人自己没这个权限（转给管理员）；② 危险操作（改权限、看密钥明文、加管理员、删资源——`需求.md` 第 5 节的底线，必须管理员本人点、验证本人）。
3. **人只看结果，不看过程**。工具、工具列表、员工之间的来回都是员工内部的事；人在会话里看到的是员工说的话和最终结果。过程全进审计，真要追查时能翻，但不推给人看。

| agent 之间委派的标准是 A2A v1.0（和 MCP 互补） | 内部派活用 Opero 内核工具（第 6 节）；以后要和外部 agent 互通再加 A2A 接口 |

## 1. 谁和谁交流（全景）

```
 人（网页 / 桌面 / 手机）
   │ 聊天消息、（少数时候）点确认卡片、填表单（MCP Apps，经宿主桥）
   ▼
┌──────────────────── Opero 后台 ────────────────────┐
│  会话与消息        工具注册表（内核 + 插件）            │
│        ╲               │                           │
│         ▶  MCP 网关：认身份 → 判定 → 审计 → 执行 ◀──┼── 外部 MCP 客户端（Streamable HTTP /mcp，令牌）
│               │                    │               │
│        后台内执行（查库、发消息）   经 Agent 到服务器执行 │
└───────────────┬────────────────────┬───────────────┘
                │ Agent 长连接（服务器主动连出）
                ▼
   服务器上的 Opero Agent（Go）
     ├─ 启动 / 驱动执行器（Claude Code、Codex…）──┐
     └─ opero-mcp 桥（stdio）◀── 执行器的 MCP 客户端 ┘
```

| 通道 | 谁发起 | 走什么 | 身份怎么来 |
|---|---|---|---|
| 执行器 → 后台工具 | 员工（AI） | 执行器 MCP 客户端 → stdio → Agent 里的 `opero-mcp` 桥 → Agent 长连接 → 网关 | 派活时后台签发的**运行令牌**（绑定 发起人 / 员工 / 会话 / 任务），Agent 持有，执行器看不到 |
| 表单 / 底部菜单 → 后台工具 | 人 | iframe postMessage → 宿主（网页 / App）→ HTTPS → 网关 | 当前登录用户；危险操作加「验证本人」 |
| 员工 → 员工 | AI | 调工具 `employee.delegate` / `employee.ask`（第 6 节） | 沿用**最初发起人** |
| 后台 → 员工 | 系统 | 往员工的执行器塞一条消息（派活、转交结果） | 系统消息，标来源 |
| 外部 MCP 客户端（Claude Desktop、别的系统、「员工对外接口」） | 外部 | Streamable HTTP `/mcp` + 令牌 | 令牌对应的用户 + 指定员工 |

**为什么执行器不直连后台 HTTP，要走 Agent 桥**：服务器只主动连出、不开端口；内网机器也能用；令牌不进执行器的环境变量和配置文件（AI 读不到、日志里不会有）；Agent 能在本机先拦一道（禁编译、敏感文件）；断线由 Agent 重连，执行器无感；执行器说哪个 MCP 版本由桥去适配。

## 1.1 执行器怎么接上 Opero 的 MCP（详见 `调研-agent-CLI.md`）

业界驱动方式已收敛成三种，Go Agent 各写一个驱动器；每种都能在**启动时把 `opero-mcp` 桥注入进去**，不用改执行器的全局配置：

| 驱动器 | 覆盖 | 注入 MCP 的方式 |
|---|---|---|
| stream-json（stdin 写消息、stdout 读事件，常驻） | Claude Code、Qwen Code、CodeBuddy、Amp… | `--mcp-config <临时文件> --strict-mcp-config`（只用 Opero 给的） |
| Codex app-server（JSON-RPC，常驻，能插话 / 中断） | Codex | `-c mcp_servers.opero…` 覆盖配置，同时配大 `tool_timeout_sec` |
| ACP（Agent Client Protocol，stdio JSON-RPC） | OpenCode、Goose、Copilot CLI、Kimi Code、Kiro、Cline、Droid… | `session/new` 时直接传 `mcpServers` |

第一批：Claude Code、Codex、OpenCode（顺带做出 ACP 通用驱动）、Qwen Code（国内模型）。
各家订阅基本都**不许用来给别人提供服务**，开源版默认引导填 API Key（和 `需求.md` 第 7 节一致）。

## 2. 网关：每次调用都一样走

```
调用进来（任何通道）
 1. 认身份 → 调用上下文 ctx（第 3 节）
 2. 找工具、校验参数（JSON Schema）
 3. 判定(ctx, 工具, 资源) → 允许 / 要确认 / 要申请 / 拒绝
 4. 执行：后台内 handler，或下发到某台 Agent
 5. 写审计（判定、结果、耗时）→ 返回统一结果（第 5 节）
```

- 第 3 步就是 `需求.md` 第 9 节的**唯一判定函数**。二开只在这里加规则。
- **默认规则（信任 AI）**：

| 情况 | 结果 |
|---|---|
| 发起人有权限 + 员工有授权（或开了自动审核） | **允许**，直接做，不问人 |
| 员工没授权，但发起人有权限（例如管理员发起） | **允许**，顺手给员工记一条授权（按系统设置的默认时长），不问人 |
| 发起人自己没权限（普通用户碰没授权的东西） | 要申请：转给管理员，一张卡片 |
| 危险操作 | 要确认：管理员本人点 + 验证本人（30 分钟内验过不再问），永远不能自动 |
| 规则明确禁止（二开加的） | 拒绝，带原因 |

- 生产保护（`需求.md` 第 5 节，「写生产先确认」）按系统设置走；**默认关**（2026-11-21 已定），要的人在系统设置里打开。
- 防线写在网关代码里，不靠提示词：AI 被日志、邮件内容诱导，危险操作也一定停下等人。
- 网关之外**没有别的路**能改数据：写操作一律是「调工具」。

## 3. 调用上下文 ctx（谁在做）

| 字段 | 说明 |
|---|---|
| `origin_user` | 最初发起的人（员工派员工时不变）——判定权限主要看他 |
| `actor` | 直接调用者：`user:<id>` / `employee:<id>` / `system` / `external:<令牌id>` |
| `employee` | 通过哪个员工 |
| `session`、`task` | 属于哪个会话、哪个任务 |
| `chain` | 派活链：[总调度 → 发布]，只用来防死循环（默认最多 5 层） |
| `channel` | `executor` / `form` / `menu` / `external` / `system` |
| `verified_at` | 最近一次验证本人的时间（只有人能有，危险操作用） |

运行令牌：派活时后台签发，**只在这次运行里有效**，绑定 ctx 的前五项；运行结束或被停止时作废。令牌本身不带权限，能做什么每次判定。

## 4. 工具声明（内核和插件一样）

工具名：`插件.动作`，小写加下划线，如 `release.publish`、`server.read_log`、`core.ask_user`。插件只能注册自己前缀的工具。**工具是给 AI 用的，不给人看**：没有「工具列表」页面，描述按 AI 能看懂写就行。

```yaml
name: release.publish
description: …               # 给 AI 看：什么时候用、注意什么
employee: release            # 属于哪个员工（它的工具默认在它的工具列表里）
risk: write                  # read / write / danger
resource:                    # 用到哪类资源，从哪个参数取
  type: app_env
  from: [app, env]
input_schema: {…}            # JSON Schema
output_schema: {…}           # 结构化结果
ui: ui://release/publish     # 可选：对应的表单（MCP Apps），给人主动操作用
visibility: [model, app]     # model = AI 能调；app = 表单 / 菜单能调
exec: backend | agent        # 后台内执行，还是下发到资源所在服务器的 Agent
timeout_s: 600
idempotent: false            # 能不能安全重试
confirm_text: "删除服务器 {name}"   # 只有 risk: danger 要写：确认卡片上的一句人话
```

- 风险级别**必须在代码里声明**，没声明的工具不让注册。
- `resource.type` 可扩展：内核有 server / credential / workspace / employee / user / setting；插件可以注册新类型（店铺、设备…），自动接上授权、审计。
- 参数里**只放凭证编号**（`credential_ref`），绝不放明文；执行时由后台或 Agent 取明文用，结果里也会被过滤。

### 员工看到哪些工具（tools/list）
- **自己的工具 + 内核通用工具**（`core.*`、`employee.*`、`task.*`）全部列出来。
- 其它员工的工具员工内部自己查：`core.find_tools(关键词)` 查、`core.call_tool(名字, 参数)` 调，照样过判定。工具太多全列会撑爆上下文，这样所有执行器都能用。
- 判定结果是「拒绝」的工具照样能查到，调用时返回原因，免得 AI 以为没有这个功能、自己写脚本绕过。
- 工具列表变了按「下次运行生效」。

## 5. 统一结果（AI 一看就懂下一步）

工具**不用 MCP 报错**表达「要确认 / 要申请 / 拒绝」，而是返回正常结果带状态。绝大多数调用是 `ok`；其它状态是少数情况：

```json
{
  "status": "ok | running | pending | denied | failed",
  "summary": "一句话",
  "data": { … },                    // ok 时的结构化结果（符合 output_schema）
  "task": "t_123",                  // running 时
  "ticket": "c_123",                // pending 时：确认单 / 申请单编号
  "reason": "删除服务器是危险操作，要管理员本人确认",
  "next": "已请管理员确认，结果会作为新消息发给你；先做别的或结束这一轮，不要重试、不要换办法绕"
}
```

| 状态 | 什么时候 | AI 该做什么 |
|---|---|---|
| `ok` | 做完了（绝大多数） | 继续 |
| `running` | 长任务已开始（编译、发布、派给别的员工） | 不用等；完成后系统发消息给它（第 8 节） |
| `pending` | 危险操作要确认 / 发起人没权限要申请（少数） | 停下这件事，等消息 |
| `denied` | 规则拒绝 | 跟用户说明原因，不要绕 |
| `failed` | 执行出错 | 看 `reason` 决定 |

- MCP 层面的 `isError: true` 只留给真正的错误（参数不对、工具不存在、执行异常）。
- 同时放 `structuredContent`（给程序）和一段文字 `content`（给 AI），文字里写清关键数据和 `next`。
- 结果太长（日志）：截断 + 存成文件，返回文件链接（resource_link），AI 需要再按段读。

## 6. AI 和 AI 之间（员工派活，自动进行）

AI 之间不开新协议，全部是内核工具。**只要发起人能用目标员工，就直接派、直接问，不经过人**：

| 工具 | 干什么 | 同步 / 异步 |
|---|---|---|
| `employee.list` / `employee.profile` | 有哪些员工、各管什么 | 同步 |
| `employee.delegate` | 派活：给某员工发一个任务（说明、期望结果、附件） | **异步**：返回 `running` + `task` |
| `employee.ask` | 问一句（不让对方动手，只要答案） | 同步等，太久（默认 5 分钟）转成异步 |
| `task.status` / `task.cancel` | 查 / 停自己派出去的任务 | 同步 |
| `task.report` | 被派活的员工交回结果（最终结果必须调它） | 同步 |

流程（总调度派给发布）：
1. 总调度调 `employee.delegate(to=release, …)` → 判定：发起人能用「发布」→ 允许。
2. 后台把任务交给「发布」的执行器（标「总调度 转来」），**身份沿用最初发起人**。
3. 发布干完调 `task.report(result)` → 后台把结果作为新消息交回总调度 → 总调度继续，最后在**用户的会话里说结果**。
4. 员工之间的来回**不推给用户**（不出现在用户的会话列表里），全进审计；用户只看到总调度说的话和最终结果。真要追查时可以在员工档案里翻（不主动展示）。

约束（只防出事，不加审核）：
- 派活链最多 5 层、同一任务不能派回链上已有的员工（防死循环）。
- 被派员工做事时照样按发起人身份判定：普通用户发起的不会因为经过总调度就变成管理员。
- 「谁能用：仅管理员」的员工，非管理员发起的派不过去（返回 `denied`）。

## 7. 人和 AI：表单、确认、提问

### 7.1 表单 = MCP Apps（人主动操作用）
- 表单主要是**人主动操作**的入口（底部菜单打开，不经过 AI）；AI 干活默认直接调工具，不弹表单。
- 插件把表单做成 `ui://插件/名字` 资源，mimeType `text/html;profile=mcp-app`；工具在 `_meta.ui.resourceUri` 声明，`_meta.ui.visibility` 对应 `visibility`，内容安全规则写 `_meta.ui.csp`。（插件清单里的 `ui` / `visibility` 加载时转成这些官方字段。）
- 宿主和界面之间用官方消息：`ui/initialize`（回 `hostContext`：主题、语言、尺寸…，Opero 额外放当前用户标签）、`ui/notifications/tool-input`（预填参数）、`tool-result`、`tools/call`（界面要做事都走它 → 网关）、`ui/message`、`ui/notifications/size-changed` 等，完整列表见 `调研-MCP现状.md`。网页宿主用官方 `@modelcontextprotocol/ext-apps/app-bridge`，按规范通过**另一个域名的沙箱代理 iframe** 加载。
- 手机 WebView 官方没有专门指引【未查到】，App 宿主层按同一套消息自己实现一次。
- 表单跑在沙箱里，不能联网、不能直连后台；只能通过宿主桥调 `visibility` 含 `app` 的工具。

### 7.2 确认卡片（只有危险操作 / 没权限时）
- 判定为「要确认 / 要申请」→ 后台在会话里放一张卡片（危险操作用 `confirm_text`；有 `ui` 的就嵌表单带上 AI 填的参数），工具返回 `pending`。
- 人点了 → 变成一次人发起的调用（带验证本人）→ 执行 → 结果作为消息发回给 AI。

### 7.3 临时提问 `core.ask_user`
- AI 真拿不准、要人选的时候才用（提示词里引导：能自己判断就别问）。字段是简单类型（文字、单选、多选、数字、是否），后台自动画成表单。
- 工具挂着等（期间发 progress 保活），人提交后答案作为工具结果返回；10 分钟没答 → 返回 `running`，答案到了再作为新消息唤醒。
- 第三方 MCP 服务器（员工自己接的）发来的 elicitation：Agent 通过 Claude Code 的 `Elicitation` 钩子 / Agent SDK 的 `onElicitation` 接住，转成同一种表单。Codex 暂时做不到。

### 7.4 「在做什么」
- Agent 读执行器的流式事件，在会话里显示一行小字（在执行命令、在读文件…），不需要 AI 配合；`core.set_status(一句话)` 可选。

### 7.5 往会话里发东西
`session.post_message`（文字 / Markdown）、`session.send_file`（文件）、`session.post_card`（几种固定样式：信息、结果、链接）。

## 8. 长任务和异步

- 编译、发布、跑脚本、派给别的员工：工具立即返回 `running` + `task`；完成后后台给员工发一条「任务 xx 完成：…」的消息，唤醒执行器继续。**不靠执行器挂着等**（执行器有工具超时，进程也可能被重启）。
- 任务状态值直接用 MCP Tasks 扩展的五个：`working / input_required / completed / failed / cancelled`。以后执行器普遍支持 Tasks 了，只是多一种通知方式，不用改表。
- 人随时能在会话里说「停」→ `task.cancel` → Agent 杀进程。

## 9. 员工的「知识」放哪、怎么拿（2026-11-22 提出：通用规范、接口放数据库，员工通过 MCP 查）

分三层：

| 层 | 放哪 | 员工怎么拿 | 为什么 |
|---|---|---|---|
| **必读**：我的习惯、员工角色（职责提示词）、安全底线 | 数据库 | **每次派活自动带上**（系统提示里，不靠员工查） | 不能漏；要短（≤ 1～2 千字） |
| **按需查**：通用规范（发版规范、编码规范…）、接口文档、知识库、流程 | 数据库（每次修改存一个版本，可退回） | **MCP 工具**：`kb.search(关键词, 类型?)` → 列表 + 摘要；`kb.get(id)` → 全文 + 版本号；`rules.get(主题)` → 某条规范；`flow.list / flow.run` | 改一次所有员工马上用上；只取需要的段落省上下文（文档太长每次全读太费）；界面能改能搜；每次查记操作记录；所有执行器都能用 |
| **自己的记忆**：交接、机器笔记、它自己的流程草稿 | 员工自己的 git 仓库 `emp-名字` | 执行器本来就在这个目录里，直接读写 | 跟着员工走，换 work、换服务器都不丢 |

- 读类工具，风险级别「读」，直接做。写（员工改知识库）是「写」，有记录、可退回。
- 导出 / 导入：知识库和规范可以导出成 Markdown（git 仓库）用于分享、员工模板、官方升级时合并；导入时按版本合并。
- 其它 MCP 资源：`ui://…` 表单界面；`opero://employee/<id>/profile` 员工档案。prompts 第一版不用。

## 11. 审计（每次调用一条，后台默默记）

`时间 · origin_user · actor · employee · channel · 会话 / 任务 · chain · 工具 · 风险级别 · 资源 · 参数摘要（凭证、密码字段打码）· 判定结果 + 原因 · 怎么批的（直接允许 / 自动审核 / 谁批 / 怎么验证）· 执行结果 · 耗时`。
只能追加，不能改、不能删（后台开发员工也不能改审计代码）。审计是出事时追查用的，不主动推给人看。

## 12. 版本

- **只按 MCP 2026-07-28 实现**，不做旧版兼容（我们是新项目，没有旧包袱）。
- 执行器作为客户端说哪个版本是它们的事：`opero-mcp` 桥是我们自己的，在本机按执行器会说的版本和它对话（用官方 Go SDK），桥到后台一律新版。所以后台只有一套代码；等执行器都跟上新版，桥里那层自然用不上。
- Opero 工具本身：工具名不变、参数只加不减；要破坏性改动就出新名字（`release.publish_v2`）。
- Agent ↔ 后台的长连接协议另外定义（Agent 协议，不在这份文档），只在里面开一个「MCP 消息透传」通道。
