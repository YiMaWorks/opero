# 打包工具（流水线）接入规范

一个项目可以有好几个**编译组件**（网页、安卓、后台…），每个组件各自选在哪编、用哪个打包工具、有自己的流水线；发布目标选发哪个组件。下面说的都是「一个组件」的事。

Opero 编译一个组件有两条路：**本地**（在服务器上编）和**流水线**（交给打包工具编）。在哪编默认「自动」：编之前看本地那台当时的空闲内存、磁盘、CPU，够就本地，不够走流水线；Android、Flutter、iOS、Unity 默认走流水线。接入项目时会自动认出项目类型、按仓库平台建好流水线（Codeup → 云效，GitHub → Actions，GitLab → GitLab CI）。

## 1. 统一约定（所有打包工具一样）

- **同一个编译脚本**：`code/server/src/build.ts` 的 `script(b, code)` 按模板（node / go / android / spring / custom）生成；本地和各家流水线跑的都是它。
- **产物**：脚本把要发的东西放进 `out/`，Opero 补 `SHA256SUMS`、`VERSION`、`COMMIT`；node / go 模板打成 `<名字>-<版本>.tgz`，包里带 `deploy.sh`（部署时 Agent 以 root 跑，`OPERO_DIR` = 部署目录）。
- **两个一次性地址**（`code/server/src/pipelines.ts`），Opero 的密码不交给打包工具：
  - 源码地址 `GET /api/build-src/<令牌>`：Opero 用自己的凭证拉好要编的那个提交（带 `.git`），打成 tgz。打包工具自己能拉代码的（云效、GitHub、GitLab）用不着。
  - 产物地址 `PUT /api/build-upload/<令牌>`：流水线最后一步 `tar czf /tmp/opero-out.tgz -C out . && curl -fsS -X PUT --data-binary @/tmp/opero-out.tgz "$OPERO_UPLOAD"`。不依赖各家「下载产物」的接口。
  - 源码地址 30 分钟、产物地址 2 小时有效，用一次就作废；Opero 要配外网地址（`OPERO_URL`），打包工具才连得回来。
- **触发时带的变量**：`OPERO_UPLOAD`（产物地址）、`OPERO_RELEASE`（这次的编号）、`OPERO_COMPONENT`（编哪个组件，同一份流水线定义里放了几个组件时用），要源码的再加 `OPERO_SRC`。
- **多个组件不能互相覆盖**：流水线名字、流水线文件、任务名、产物名都要带上组件（`build.ts` 的 `codeOf(w, b)`；编号 `main` 的组件不带后缀）。

## 2. 接一个新的打包工具要写什么

1. `build.ts`：`BuildCfg.provider` 加一个值、配置字段（凭证、任务名…）；`pipelineReady`、`PIPE`（显示名）、`generate`（建 / 更新流水线）、`run` 里分派到新函数。
2. `pipelines.ts`：三个函数——`xxxGenerate`（建 / 更新流水线定义，里面跑 `script()` 的内容 + 上传产物那两行）、`xxxRun`（触发、每 10 秒查状态、失败取日志、成功后 `uploadUrl().wait()` 等产物，再 `unpack`）。
3. 凭证：`code/web/src/credmeta.ts` 加一个类型（字段、获取步骤、直达链接、要的权限）；`code/server/src/creds.ts` 加测试连接（能列出任务 / 项目最好）。
4. 网页：`code/web/src/pages/live2.tsx` 的 `PROVIDER` 加显示名，编译设置里选它时要填的（比如凭证）。
5. 记进本文件第 4 节，以及 `docs/设计.md`。

## 3. 已接的

| 打包工具 | 认证 | 流水线定义 | 拿代码 | 状态 |
|---|---|---|---|---|
| 云效 Flow | Codeup 个人访问令牌（要有流水线读写） | 云效里的流水线（API 建 / 改 YAML） | 云效自己拉（Codeup 服务连接） | 能用 |
| GitHub Actions | 项目的 GitHub 令牌（workflow 权限） | 仓库里 `.github/workflows/opero-build-<组件>.yml`（每个组件一个） | Actions 自己拉 | 能用 |
| GitLab CI | 项目的 GitLab 令牌（api 权限） | 仓库里 `.opero/gitlab-ci.yml`（每个组件一个任务 `opero-build-<组件>`，按 `OPERO_COMPONENT` 只跑一个），根 `.gitlab-ci.yml` include 它（没有就建） | GitLab 自己拉 | 代码写好，待调试 |
| Jenkins | 「凭证 → 其它 → Jenkins」：地址、用户名、API Token | 每个组件一个自由风格任务 `opero-<项目>-<组件>`（不用装插件），参数 `OPERO_SRC` / `OPERO_UPLOAD` / `OPERO_RELEASE` | 从源码地址下载 | 代码写好，待调试 |

## 4. 调试步骤（GitLab / Jenkins）

1. Opero 配好外网地址（`OPERO_URL`），从打包工具那边能打开 `https://你的地址/`。
2. **GitLab**：「凭证 → 代码仓库 → GitLab」加令牌（api、read_repository、write_repository），接入 GitLab 仓库时选它；项目「编译 → 改」打包工具选 GitLab CI →「生成流水线」→ 看仓库里有没有 `.opero/gitlab-ci.yml` 和 include。
   **Jenkins**：「凭证 → 其它 → Jenkins」填地址、用户名、API Token，测试连接能列出任务；项目「编译 → 改」打包工具选 Jenkins、选这个凭证 →「生成流水线」→ Jenkins 里应出现 `opero-<项目名>` 任务。
3. 编译设置「在哪编」选「总是流水线」→「试编译」→ 看日志：
   - 卡在触发：看令牌权限（GitLab 要 api；Jenkins 用户要 Job/Build）。
   - 流水线失败：日志里有打包工具那边的输出（GitLab 取出错 job 的日志，Jenkins 取 consoleText）。
   - 「产物没传回来」：打包工具连不上 Opero 的外网地址，或者 curl 被代理拦了。
4. 编通了，「在哪编」改回「自动」。
