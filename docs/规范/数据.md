# 数据规范（草案 v0.2，2026-11-21）

> v0.2 改动：说明 Opero 的出发点是**解决开发的问题**，没打算给运营用。所以主场景从「运营看业务数据」改成「**开发排查 / 修数据时查库**」；v0.1 的「实体 / 业务对象」层降为可选，留给以后二开给运营用。
> 原来的想法是「一个员工负责查库」——方便，但不直观：结果是一段文字或一张死表，看不到它跑了什么 SQL，排查时还得在「查库员」和「日志员」之间来回转述。

## 0. 核心思路

1. **谁在排查谁就直接查库**：不单设「查库员」。查库是内核通用能力，日志值班、后台开发、运维等员工排查时自己查——日志、代码、数据库在同一个员工的上下文里，不用转述。（想要一个专门查库的员工也可以建，用的是同一套能力。）
2. **结果是一张能操作的「查询卡片」，不是一段文字**：AI 写 SQL，后台执行，界面直接展示结果。

```
「看下用户 10086 最近的订单，为什么支付失败」
  员工（mov 日志值班）查日志 → 写 SQL → 查库
  ┌ 查询 · mov-prod（只读）· 23 ms · 5 行       [SQL ▾] [复制] [导出] [存成菜单] ┐
  │ id     status   pay_channel  err_code   created_at                         │  ← 真表格：排序、筛选、展开 JSON 列、
  │ 98213  failed   wechat       SIGN_ERR   09:41                              │     点外键跳到关联表的那一行
  │ ...                                                                         │
  └─────────────────────────────────────────────────────────────────────────────┘
  员工：最近 5 单都是 SIGN_ERR，09:40 起开始，和日志里换密钥的时间一致……
```

- **SQL 看得见**（开发要看）：卡片上能展开 SQL、复制去自己的客户端跑。
- **AI 和界面各拿各的**：AI 拿到前几十行（敏感列打码）用来判断；完整结果由界面直接向后台取（分页、排序、导出不经过 AI，不受 AI 输出长度限制、不花 token）。
- **常用查询存成菜单**：点「存成菜单」→ 变成员工的底部菜单（如「今天失败的支付」），以后一点就开，不经过 AI；可以带参数（用户 ID、日期）。

## 1. 数据源

- 数据源 = 一种资源：业务库（第一版 MySQL；PostgreSQL 等按需加），带环境标签（开发 / 测试 / 生产），连接凭证在凭据中心，AI 只拿编号。
- 每个数据源配**只读账号**和（可选）**可写账号**，分开授权。
- 员工的底部菜单可以有「库表结构」面板：表、字段、索引、注释，开发常用；AI 写 SQL 前也先读结构。

## 2. 改数据（开发修数据）

开发经常要修数据。按「信任 AI」原则：有权限就直接做，但**一定能撤销**：

1. AI 写 UPDATE / DELETE / INSERT → 网关先用同样的条件 **SELECT 出将受影响的行**，存成快照；
2. 结果卡片显示「改了 N 行 · 改前 / 改后对比 · [撤销]」；
3. 撤销 = 用快照写回（有时间限制，比如 7 天，快照过期自动清理）；
4. 影响行数超过阈值（默认 1000）或没有 WHERE 的语句 → 当危险操作（要人确认），这是底线。
5. 改表结构（DDL）一律当危险操作。

## 3. 安全底线（写在代码里）

- 查询有超时和行数上限；大表全表扫描先提示。
- 敏感列（手机号、身份证、密码、token…）按列名规则 + 手工标记打码；AI 和界面拿到的都是打码值，看明文 = 危险操作。
- 所有 SQL（读写都算）进审计：谁、哪个员工、哪个库、语句、影响行数、耗时。

## 4. 以后给运营用（二开 / 插件，不进第一版）

v0.1 的思路留在这里备用：在数据源上加「实体」层（表 → 业务对象、字段显示名、能做的操作），查询卡片的条件变成可点的标签（订单 · 今天 · 城市=上海），运营不用看 SQL。内核留扩展点，第一版不做。

## 5. 和别的规范的关系

- 查询卡片、库表结构面板 → `表单与卡片` 规范 / 设计系统。
- 写 SQL 的快照撤销 → `工具` 规范的 `undo`。
- 存成菜单 → `员工` 规范（底部菜单）。
- 新的数据源类型（PG、ClickHouse、Redis、Mongo…）→ `插件` 规范。
